# Security review log (STATUS L12)

Findings from reviewing issuance, revocation and verification, each fixed in the commit that
mentions L12 and covered by the tests it names. STATUS L12 holds the current state; this file
keeps the detail so STATUS stays readable. Add new findings at the end.

## Standing measures

Self-review done (delegation fixes in 8c68a50); budget guards (daily issuance limit, per-credential monthly renewal cap, master plan §5.4/§10) in the dashboard; HMAC-signed tokens (`dbae_`, `dbamcp_`, poll tokens…) accept only the canonical base64url tag, so no token has a second valid spelling.

## Found and fixed

- A repeated `Idempotency-Key` on `POST /credentials` (and two approvals of one enrollment racing) issued a second, unpaid credential outside the daily limit; a retry now returns the first credential, a different request with the key gets 422 `idempotency_key_reused`, and OpenAPI lists the header only on routes that honour it.
- Issuing to a revoked device's key silently reinstated it on every path, so a stolen, revoked device holding a fleet token could re-enroll itself; now only a person with a recent sign-in (or an API key) reinstates (`device.reinstated` audited), token redemption and delegation get 403 `device_revoked` (master plan §10); likewise rotating a credential onto a revoked device's key (403 `device_revoked`) or another live device's key (409 `key_in_use`), which overwrote that device's record.
- After a key rotation the old version (old key) still passed online `/authorize`, which checked only `revoked_at`, and DBA's own API whenever the new status entry reused the old index in another shard (indexes are per shard; the check compared the index alone), so a rotated-away key kept working; both now compare the (index, list URI) pair.
- Online `/authorize` refuses access tokens once the audience sets `accept_access_tokens: false`, and a grant out of uses no longer spends (or asks for) a step-up approval.
- DBA's own API checked DPoP proofs for method, URL and age but not reuse, and DPoP does not sign the body, so captured headers could be replayed within the proof window with another body (say, delegating a credential to the captor's key); each proof is now accepted once per account (401 `replayed_proof`, held in the AccountDO like online `/authorize`'s cache).
- DBA's API evaluated a device's `dba:*` grants with `online: true` but never enforced the usage counters or step-up approvals that returns, so a `dba:credentials:issue` grant limited to 3 uses a day (or needing approval) was unlimited; such grants no longer count there, and issuance refuses `limits.uses`/`require.step_up` on grants with `dba:` actions (400 `invalid_grants`).
- Audience OIDC redirect URIs passed with any scheme whose host was `localhost`, so an audience owner could register `javascript://localhost/…`, and the consent page (which follows the redirect even on Cancel) would run their script on devicebasedauth.org with the victim's session; redirect URIs now follow the MCP clients' rule (https, or http on a loopback address; no fragment or credentials), `/oauth/authorize` refuses other schemes for records stored earlier, and the consent page follows only http(s) addresses (enrollment `return_origin` likewise http only on localhost); `/oauth/userinfo` no longer answers for MCP apps' access tokens.
- An API key (or MCP app) with only `credentials:issue` could issue a credential or enrollment token granting `dba:session` (or any `dba:` scope), so a narrow CI key became a device with every scope; keys now grant `dba:` actions only within their own scopes, named exactly (403 `insufficient_scope`).
- The relying-party verifiers (JS, Python, Go) refetched the JWKS on every credential with an unknown `kid`, so anyone could make a site fetch DBA's JWKS once per request; a forced refetch now happens at most once per 30 s (`jwksCooldown` / `jwks_cooldown` / `JWKSCooldown`).
- `GET /audiences?mine=1` (a public route that authenticates itself) skipped the `audiences:read` scope check and read metering, so any key or `dba:` device read its audiences' full records, webhook URLs included, for free; delegation is now one level deep as master plan §13 says (a delegated credential holding `dba:credentials:issue` could delegate again; now 403 `delegation_depth`).
- `limits.uses` multiplied two ways in online `/authorize`, whose counters were per credential and grant index: each delegated credential (which must copy its parent's limit) got a fresh counter, so a device limited to 3 uses a day could delegate itself any number more, and an access token (which keeps only its audience's grants, so its indexes shift) spent another grant's counter or a fresh one; delegates now spend the parent grant's counter (`usage_from`, recorded at issuance) and token indexes map back to the credential's (`src/usage-limits.test.js`, spec/evaluation.md §3.5).
- Step-up approval routes accept dashboard devices (`dba:session`), so a credential holding both `dba:session` and a `require.step_up` grant approved its own requests; a device can no longer approve a request it made (403 `self_approval`; it may still deny).
- A device-reported location with a negative `acc_m` shrank the distance instead of widening it, so `acc_m: -1e7` matched any `where.source: "device"` area; negative accuracy now never matches, like a missing one (JS, Python, Go; vector "negative device accuracy never matches").
- A delegating device could name audiences its own credential lacked (enrollment tokens already refused this), so a delegate could identify the account to a site its delegator could not reach; delegated `aud` must now be within the delegator's (403 `not_narrower`).
- The relying-party verifiers (JS, Python, Go) accepted a status list with no `exp`, and took each refetched list as is, so a stale CDN copy from before a revocation brought the credential back until the next refetch; lists must now carry `exp`, and every bit a verifier has seen set stays set (the issuer never clears one; spec/credential.md §7).
- `dba curl` put the credential and DPoP proof on curl's command line, where any local user can read them (ps); since DPoP does not sign the body, the proof could be raced to the same URL with another body; the headers now go through a private 0600 file (`-H @file`, curl 7.55+).
- (found by an independent review of the attestation code): the TPM attestation chain checked only signatures, so one genuine Microsoft-issued AIK (a restricted TPM key signs any data not starting `TPM_GENERATED`, a TBSCertificate included) could issue a certificate for a software key and get it attested `security_level: tpm`, satisfying `require.attestation: hardware`; every certificate above the leaf must now be a CA (basicConstraints cA, keyCertSign when keyUsage is present, pathLenConstraint; `requireCaChain`, also applied to Android chains as defense in depth), and the AIK certificate must carry basicConstraints with cA false (WebAuthn §8.3.1); a malformed basicConstraints in `ek_chain` gave a 500, now 400.
- The hourly caps on recoveries anyone may start (three by gate and three by email per account, each pushing or emailing the owner and possibly charging them a gate request or an email) were counted in the account object's memory, which starts from zero whenever the object is evicted after a short idle, so a stranger who paused between bursts could flood an owner and drain their balance; the counts are now on the profile row (`src/recovery.test.js`, `src/email-recovery.test.js` restart the object between starts).

## Known limits

- A stolen `dba:session` device can still issue itself a new non-`dba:` credential without step-up (only `dba:*` issuance needs a recent sign-in), so `dba:session` remains as strong as the owner's session.
- An independent review is still needed (STATUS L12).
