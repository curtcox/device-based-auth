Phones and PCs: Android, iOS and TPM

Native devices keep their key in hardware and can prove it to the issuer with key attestation, so grants can require require.attestation: "hardware". The rest of the API is the same as for every device: see the docs.

  1. Quick start: Android
  2. Quick start: iOS and App Attest
  3. PCs: TPM key attestation

Quick start: Android

docs/samples/android is two files to copy into an app (API 26+, no dependencies): AndroidKeystoreKeys generates a P-256 signing key inside the Android Keystore (StrongBox when the phone has one), and DbaClient sends the signed enrollment request, waits for approval and signs a DPoP proof for each call. The key never leaves the secure hardware; only its public half is sent. Run the calls off the main thread.

String challenge = DbaClient.attestationChallenge(origin);              // for key attestation
AndroidKeystoreKeys keys = AndroidKeystoreKeys.create("dba-device", challenge);
DbaClient client = new DbaClient(origin, keys.privateKey(), keys.publicKey());
String credential = client.enroll(List.of("hashbin.org"), grants,
    DbaClient.map("name", Build.MODEL, "kind", "phone", "key_protection", keys.keyProtection()),
    keys.attestation(challenge),                                            // the Keystore's certificate chain
    url -> startActivity(new Intent(Intent.ACTION_VIEW, Uri.parse(url))));   // owner approves
Object result = client.call("POST", "https://hashbin.org/api/content", credential, body);

Because the key was generated with devicebasedauth.org's challenge, the Keystore's certificate chain proves to the issuer that the key lives in a TEE or StrongBox and was never exported. The approval page and the credential then say Android Keystore, attested by Google (with the verified-boot state) instead of self-reported, in device.attestation (spec §3a). The attestation also names the app that made the key, so a grant can pin your app with "require": { "app_ids": ["android:com.example.app:<sha256>"] }, where the digest is your signing certificate's SHA-256 as lowercase hex (apksigner verify --print-certs, or the Play Console's app signing page without the colons); it counts only on phones with verified boot and a locked bootloader. A rejected chain fails the enrollment with invalid_attestation; leave out the attestation to enroll without one. On later runs use AndroidKeystoreKeys.load("dba-device").

The same DbaClient runs in CI on a plain JVM with a software key (Main.java, below), against a local server, and the Keystore class is type-checked against the Android API there:

        DbaClient client = new DbaClient(origin, key.getPrivate(), (ECPublicKey) key.getPublic());

        List<Object> grants = List.of(DbaClient.map("actions", List.of("hashbin:content:write")));
        Map<String, Object> device = DbaClient.map("name", "Android sample", "kind", "phone", "key_protection", "software");
        String credential = client.enroll(Collections.singletonList("hashbin.org"), grants, device, url -> {
            System.out.println("Ask the account owner to approve this device:");
            System.out.println(url);
            System.out.flush();
        });
        String payload = new String(Base64.getUrlDecoder().decode(credential.split("\\.")[1]), java.nio.charset.StandardCharsets.UTF_8);

Store the credential next to the key alias (it is not secret) and renew it at about two thirds of its lifetime with client.call("POST", origin + "/api/v1/credentials/" + cid + "/renew", credential, DbaClient.map()), as Main.java does. For iPhone and iPad see iOS.

Quick start: iOS and Apple App Attest

docs/samples/ios is a Swift package (iOS 15+, Foundation, CryptoKit and DeviceCheck only) to copy into an app or depend on: SecureEnclaveKeys generates the P-256 signing key inside the Secure Enclave and keeps only its encrypted handle in the Keychain (this device only), AppAttest has App Attest vouch for it, and DbaClient sends the signed enrollment request, waits for approval and signs a DPoP proof for each call.

let key = try SecureEnclaveKeys.loadOrCreate(name: "dba-device")
let client = DbaClient(origin: "https://devicebasedauth.org", key: key)
let challenge = try await client.attestationChallenge()
let attestation = try await AppAttest.attestation(for: key, challenge: challenge, appId: "ABCDE12345.org.example.wallet")
let credential = try await client.enroll(audiences: ["hashbin.org"], grants: grants,
    device: ["name": UIDevice.current.name, "kind": "phone", "key_protection": "secure-enclave"],
    attestation: attestation) { url in UIApplication.shared.open(URL(string: url)!) }   // owner approves
let result = try await client.call("POST", "https://hashbin.org/api/content", credential: credential, body: body)

CI builds the package on macOS, type-checks it for iOS, and runs the same DbaClient against a local server with a software key (Sources/dba-sample/main.swift; CI machines have no Secure Enclave):

    var credential = try await client.enroll(
        audiences: ["hashbin.org"],
        grants: [["actions": ["hashbin:content:write"]]],
        device: ["name": "iOS sample", "kind": "phone", "key_protection": "software"]
    ) { url in
        print("Ask the account owner to approve this device:")
        print(url)
        fflush(stdout)
    }

What the attestation proves:

App Attest cannot vouch for an arbitrary key: Apple attests a key of its own and says which app, on a genuine iPhone or iPad, holds it. So an iOS app makes its DBA key in the Secure Enclave as usual and then has App Attest vouch for that key:

  1. Get a challenge from POST /api/v1/enrollments/attestation-challenge (valid 10 minutes).
  2. Generate the P-256 signing key in the Secure Enclave and compute its JWK thumbprint (RFC 7638).
  3. Call DCAppAttestService.shared.generateKey(), then attestKey(keyId, clientDataHash:) with the SHA-256 of the UTF-8 string "<challenge>.<thumbprint>".
  4. Add attestation: { format: "apple-appattest", challenge, app_id: "TEAMID.bundle.id", key_id, object } (key_id and object base64) to the signed enrollment request.

The issuer checks Apple's certificate chain, the nonce, the key id, the app id and the counter (spec §3a) and signs { format: "apple-appattest", security_level: "secure_enclave", app_id, environment } into device.attestation; the approval page says Secure Enclave, reported by the app … as attested by Apple. Because what Apple proves is the app, not the key, a grant counts it for require.attestation only when it also names the app in require.app_ids, and only for production builds:

{ "actions": ["hashbin:content:write"],
  "require": { "attestation": "hardware", "app_ids": ["ABCDE12345.org.example.wallet"] } }

PCs: TPM key attestation

On a PC with a TPM 2.0, keep the DBA key in the TPM and have the TPM's attestation identity key (AIK) certify it. Windows gets an AIK certificate from Microsoft after checking the TPM's endorsement certificate, so the issuer can trust it:

  1. Get a challenge from POST /api/v1/enrollments/attestation-challenge (valid 10 minutes).
  2. Create a P-256 signing key in the TPM (Windows: the Microsoft Platform Crypto Provider) and compute its JWK thumbprint (RFC 7638).
  3. Certify it with the AIK (TPM2_Certify; on Windows NCryptCreateClaim with the "Windows AIK") using qualifying data = SHA-256 of the UTF-8 string "<challenge>.<thumbprint>".
  4. Add attestation: { format: "tpm", challenge, alg, x5c, sig, cert_info, pub_area } to the signed enrollment request: alg -257 (RS256) or -65535 (RS1), x5c the AIK certificate and its CA (base64 DER), and the signature, TPMS_ATTEST and TPMT_PUBLIC in base64.

The issuer checks the chain to Microsoft's TPM root and its revocation list, the AIK certificate, the signature, that the certified key is the enrolled key, and that it was generated in the TPM and cannot leave it (spec §3a). It signs { format: "tpm", security_level: "tpm", tpm_manufacturer } into device.attestation, which satisfies require.attestation: "hardware" (not "strongbox", and not require.verified_boot).

Linux and other TPMs without a Microsoft AIK certificate

Here the TPM proves that its attestation key (AK) sits beside its endorsement key (EK), whose certificate the TPM's manufacturer issued. The device key is the same TPM-resident P-256 key; with tpm2-tools that is tpm2_createek, tpm2_createak, tpm2_create with fixedtpm|fixedparent|sensitivedataorigin|sign, and tpm2_certify:

  1. Get a challenge as above.
  2. POST /api/v1/enrollments/tpm-activation with { challenge, ek_certificate, ak_pub_area, pub_area, cert_info, sig }, all base64: the RSA-2048 EK certificate (tpm2_nvread 0x01c00002), the AK's public area, the device key's public area, and the certify's TPMS_ATTEST and TPMT_SIGNATURE. Add ek_chain if your EK certificate's CA is not one DBA knows but chains to one.
  3. The answer holds a secret only your TPM can unwrap, as credential_blob (the file tpm2_activatecredential -i reads) or as id_object and encrypted_secret, and an activation token. Unwrap it with TPM2_ActivateCredential (AK and EK loaded; the EK needs a policy session with tpm2_policysecret -c e).
  4. Add attestation: { format: "tpm-ek", challenge, activation, secret } (the secret base64) to the signed enrollment request, within 10 minutes.

A complete shell script, run in CI against a software TPM, does all of this and then signs each request's DPoP proof with tpm2_sign: docs/samples/tpm/enroll-tpm.sh. The dba CLI does the same for you with dba enroll --key-store tpm (docs/samples/tpm/dba-cli.sh, also run in CI). A key rotated with dba renew --rotate moves to a new TPM key, but the renewed credential carries no attestation until the device enrolls again.

The issuer checks the EK certificate against the TPM manufacturers' EK CAs (Infineon, STMicroelectronics, Nuvoton, Intel, Nationz), the AK's attributes and signature, the certified key, and the returned secret, checks the EK certificate (and any CA you sent in ek_chain) against its manufacturer's revocation list when the certificate names one (an unreachable list answers 503 attestation_unavailable; try again), then signs the same { format: "tpm", security_level: "tpm", tpm_manufacturer }. The EK certificate is not stored. Virtual TPMs (cloud vTPMs, swtpm) are not trusted.
