Concepts

devicebasedauth.org issues device credentials: signed, readable statements of what one device may do, for which sites, when and where. The device holds the private key; we only ever see the public key.

TermMeaning
AccountA devicebasedauth.org customer with a prepaid balance in micro-dollars. Its id appears in credentials as acct. Made by paying with a device, no password needed (accounts), or by signing in.
DeviceAnything that can hold a private key: a browser profile, phone, laptop, server, CLI, CI job or AI agent. Identified by dev_… and its key thumbprint.
AudienceA site or API that accepts credentials (a domain such as hashbin.org). It owns an action namespace and publishes an action catalog. The first-party audiences are devicebasedauth.org (dba:, this service's own API), hashbin.org (hashbin:), cronly.org (cronly:) and subetha.us (subetha:session, subetha:publish, subetha:subscribe; resources are topic names or @handle/*); GET /api/v1/audiences lists every catalog.
ActionA namespaced verb from a catalog: hashbin:content:write, cronly:run, dba:session. ns:* matches every action in a namespace.
Grant{ actions, resources, when, where, net, limits, require }. A credential holds 1–32 grants; a request is allowed when at least one grant passes. Nothing is allowed by default.
CredentialA compact JWS (ES256) signed by devicebasedauth.org binding a device public key to grants for one or more audiences.
ProofA DPoP proof (RFC 9449): a tiny JWS signed by the device key for one request (method, URL, time, credential hash).
Status listA signed, compressed bitstring; bit n set means the credential at index n is revoked.
EnrollmentThe device sends its public key and the grants it wants; the account owner approves (or narrows) them on an approval page; the credential is issued.

How it fits together

  1. The device makes a key pair (non-extractable where the platform allows) and asks to enroll.
  2. The account owner opens the approval link, reads the request in plain English, and approves it. The account pays the issue price.
  3. The device sends Authorization: DBA <credential> and a fresh DPoP proof with each request.
  4. The site verifies offline with @devicebasedauth/verify (free), or asks POST /api/v1/authorize for usage limits, step-up approval and instant revocation (metered, paid by the site).
  5. The owner can revoke the credential, the device, or everything, at any time.

The credential format

A credential is header.payload.signature, each base64url. The payload is plain JSON; decode it with one base64url decode, or paste it into the inspector. The normative description is spec/credential.md; grant evaluation is spec/evaluation.md, with conformance vectors in spec/vectors.

{ "typ": "dba-device+jwt", "alg": "ES256", "kid": "dba-2026-11" }

  "sub": "dev_7Q2M9X4K1B",

Present it with a proof made by the device key:

Authorization: DBA <credential>
DPoP: <proof: {"typ":"dpop+jwt","alg":"ES256","jwk":{…}} . {"jti","htm","htu","iat","ath"[,"nonce"][,"loc"]}>

Credentials are not secret — they are useless without the private key — but every site you show one to can read its device name and places. Keep geofences coarse and device names generic where that matters. Unknown grant members make that grant deny, so new constraint types can never silently over-grant on old verifiers.

Quick start: browser SDK

The SDK makes a non-extractable P-256 key with WebCrypto and keeps it in IndexedDB: scripts on your origin can sign with it, but nothing can read it out. Enrollment opens the approval page in a popup, so call it from a click handler. Pin a versioned copy with Subresource Integrity in production (/sdk/v1.4.0/dba.js; versions before v1.4.0 do not answer DPoP nonce challenges, so their first requests after an idle spell can fail; hashes in /sdk/integrity.json). The unversioned /sdk/dba.js also answers the timed challenges of round-trip rules, which no pinned release does yet. Do not use v1.0.0: its autoRenew() renews in a loop for credentials living longer than about 37 days.

<script type="module">
  import { DBA } from 'https://devicebasedauth.org/sdk/dba.js';

  const dba = new DBA();            // new DBA({ origin, name }) for another server or a second identity
  document.querySelector('#connect').addEventListener('click', async () => {
    if (!await dba.ready()) {
      await dba.enroll({
        aud: ['hashbin.org'],
        grants: [{ actions: ['hashbin:content:write'], limits: { spend_usd_per_month: 5 } }],
        device: { name: 'Notes app on my laptop' },
        lifetime_seconds: 30 * 86400
      });
    }
    dba.autoRenew();                 // renews at 2/3 of the lifetime while the page is open
    const response = await dba.fetch('https://hashbin.org/api/content', { method: 'POST', body: 'hello' });
    console.log(response.status, dba.describe());
  });
</script>
MethodWhat it does
ready()Loads the stored key and credential; true when an unexpired credential exists.
enroll(request, { popup, onApprovalUrl, timeoutMs, enrollmentToken })Signs an enrollment request with a new key, opens the approval page and resolves with the credential (by postMessage, or by polling when approved elsewhere). With an enrollment token it is issued at once, with no popup.
fetch(input, init)fetch() with the credential and a fresh proof attached. When the server answers with a DPoP nonce challenge (401 use_dpop_nonce and a DPoP-Nonce header, RFC 9449 §8) it sends the request once more with the nonce; api() and fetchWithGates() do the same. (v1.4.0)
nonceChallenge(url, response)For your own fetch code with headers(): keeps the nonce a response hands out for later proofs to that origin, and is true when the response is a nonce challenge, so send the request again with new headers. (v1.4.0)
headers(method, url, { location })Just the Authorization and DPoP headers for one request (and DBA-Confirmation for a credential issued with confirm). location ({ lat, lon, acc_m, t }) goes into the proof as loc, for grants with where.source: "device"; fetch() takes it as init.dba.location.
fetchWithGates(input, init, { timeoutMs, onPending })Like fetch(), but while the site answers 403 gate_pending (its online check waits for the grant's gates) it sends the request again with a fresh proof every retry_after seconds. onPending(gate_request) is called once, to tell the user who must approve. (v1.2.0)
confirm({ timeoutMs, onPending })For a credential issued with confirm: asks its gates to confirm the device and waits; headers() and fetch() send the confirmation and call this by themselves when it is missing or about to end (pass { dba: { confirm: false } } to fetch to never wait). (v1.2.0)
allows(action, { resource, location })A local hint for UI (time, place and action checks only); servers still decide.
credential, payload, describe(), expiresIn(), confirmationThe credential (compact JWS), its decoded payload (unverified), its grants in plain English, seconds left, and the saved confirmation while it is current.
api(path, { method, body, auth })Call devicebasedauth.org's own API (auth: true signs with the credential); failures throw a DBAError whose code is the server's.
renew({ rotate }), autoRenew({ onError }), keyWithdrawn()Renew (or move to a new key) before expiry; autoRenew() also renews at once, free, if the issuer withdrew the key that signed the credential.
token(audience)A 10-minute bearer access token for code that cannot sign each request.
signUp({ creditCents, acceptTerms }), recover({ account, code } | { account, via: 'gate' } | { email, via: 'email' }), pending, finish({ timeoutMs, onPending })On devicebasedauth.org itself (v1.3.0): create an account by paying its first deposit with a new key, or get back in after losing every device (both take { replace: true } to start over in a slot whose credential still works); finish() waits for the payment or the recovery and keeps the credential. What waits survives page loads (pending).
revoke(), forget()Revoke this credential everywhere and delete the key; or only delete it locally.
DBA.inspect(credential)Decode any credential for display (no verification).

Quick start: CLI

The dba CLI never sends the key anywhere. It keeps it in the OS secret store when there is one (the macOS Keychain, the Secret Service through secret-tool on Linux, or on Windows sealed with DPAPI for your Windows account, through the built-in Windows PowerShell), and the credential then says key_protection: "os-keychain"; otherwise in a 0600 file under ~/.config/dba/<profile>/ ("software"). --key-store os or file (or DBA_KEY_STORE) makes the choice explicit. On a PC with a TPM 2.0 and tpm2-tools, --key-store tpm makes the key inside the TPM, where it stays: the TPM signs every request, and dba proves to the issuer that the key is there (TPM attestation), so the credential satisfies grants that require hardware. On Windows, --key-store tpm makes the key in the TPM through the Microsoft Platform Crypto Provider, with nothing to install; those keys are not attested yet, so grants that require hardware deny them. dba help lists every command.

# 1. Make a key and ask for permission to publish on hashbin.org. This prints a link; the
#    account owner opens it, checks the grants and approves. The command waits for that.
dba enroll --aud hashbin.org --action hashbin:content:write --name "Sample laptop" --wait 300

# 2. What may this device do?
dba status

# 3. Headers for one request (the DPoP proof is single-use and names this method and URL).
dba headers POST https://hashbin.org/api/content

From docs/samples/enroll-and-call.sh, which runs in CI against a local server.

dba curl -sS https://hashbin.org/api/content -d 'hello'          # curl with the headers added
curl -H "Authorization: Bearer $(dba token --aud hashbin.org)" https://hashbin.org/api/content
dba enroll --aud hashbin.org --grant '{"actions":["hashbin:content:*"],"where":{"source":"network","countries":["US"]}}'
dba renew --rotate                                                 # renew onto a fresh key
dba revoke                                                         # revoke and delete the key
DBA_API_KEY=dbak_… dba list --status active                       # every credential on the account

Also: dba status --online (or whoami) asks the server too; dba sign METHOD URL prints only the proof; dba inspect CREDENTIAL|- decodes any credential and asks the server about its signature and revocation; dba import saves a credential issued for this profile's key; dba signup and dba recover create or get back into an account (accounts). --profile NAME keeps several devices apart and --origin URL (or DBA_ORIGIN) picks the server; files live in $DBA_HOME/<profile>/ (default ~/.config/dba/<profile>/).

Like the browser SDK, the CLI renews for you: dba headers, sign, curl, token, certificate and status --online renew the credential first once two thirds of its lifetime has passed. If that fails (say the balance is too low) they warn and use the current credential, which is still valid. A device that runs rarely can renew from cron with dba renew --if-due; turn automatic renewal off with --no-renew or DBA_AUTO_RENEW=0.

Gates and confirmation from the CLI

A machine can be a gate: enroll it with dba:approvals:answer, add it with dba gates add --kind dba-device (an API key with gates:write; a device cannot change gates), and answer what waits for it with dba approvals. A credential issued with confirm asks its gates with dba confirm; dba headers and dba curl then send the saved confirmation as DBA-Confirmation and ask for a new one when it runs out (DBA_AUTO_CONFIRM=0 turns that off).

DBA_API_KEY=dbak_… dba gates add --kind dba-device --label "Build box" --device dev_…
dba --profile phone approvals --watch                              # list requests as they arrive
dba --profile phone approvals allow gtr_…                          # or deny; --number NN for sign-ins
dba --profile laptop confirm                                       # wait for the gates, save the confirmation
dba curl --dba-wait=120 -X DELETE https://hashbin.org/api/content/abc  # resend while the site answers gate_pending

See docs/samples/approve-from-cli.sh, which runs in CI against a local server.

Agents and other programs that cannot wait can use dba enroll --print-request to get a signed request, submit it (for example through the MCP request_enrollment tool), and finish with dba import.

Fleets: enrollment tokens

To enroll many machines without approving each one, create an enrollment token in the dashboard (Enrollment tokens) or with POST /api/v1/enrollment-tokens ({name, aud, grants, lifetime_seconds, max_uses, expires_in_days}, by default 1 use and 7 days; a session or an API key with credentials:issue). The dbae_… secret is shown once; GET /api/v1/enrollment-tokens lists them and DELETE /api/v1/enrollment-tokens/{id} revokes one. Each machine still makes its own key, then:

DBA_ENROLLMENT_TOKEN=dbae_… dba enroll --name build-runner-7        # the token's aud and grants apply
await dba.enroll({ device: { name: 'Kiosk 1' } }, { enrollmentToken }) // browser SDK, no popup

Under the hood that is POST /api/v1/enrollments/redeem with {request, enrollment_token}, where request is the usual dba-enroll+jwt; it may narrow the token's audiences, grants and lifetime but never widen them. Each device costs the issue price, paid by the token's account; the token stops after max_uses devices (at most 10,000), on its expiry (at most 90 days), or when revoked. Credentials record which token issued them. A device signed in with a delegated credential cannot create tokens.

Verify requests on your server

@devicebasedauth/verify is a zero-dependency ES module for Workers, Node 22+, Deno, Bun and browsers. It fetches and caches the issuer's JWKS (1 hour) and status lists (at most 5 minutes) and keeps a proof-replay cache, so most requests verify without any network call. Create one verifier per process and reuse it.

const dba = createVerifier({ issuer, audience: 'hashbin.org' });

/** What a route handler does: verify, then allow or refuse with the reasons. */
async function check(label, request, action) {
  const result = await dba.verifyRequest(request, { action });

From docs/samples/verify-request.mjs, which runs in CI against a local server.

verifyRequest(request, { action, resource, location }) returns { allow, status, code, reasons, grant_index, caveats, online_required, account, device, credential_id, credential }. status is the HTTP status to answer with: 401 for a missing, invalid, replayed or revoked credential, 403 when no grant allows the action, 503 when keys or status lists cannot be fetched (it fails closed). Map account to your own user once (for example with Sign in with devicebasedauth.org) and refuse unlinked accounts.

When to go online

Grants with limits.uses, require.online or require.step_up deny offline with code: "online_required". Ask devicebasedauth.org instead — metered at the decision price and paid by your audience account — with an API key that has the authorize scope:

import { createVerifier } from '@devicebasedauth/verify';

const dba = createVerifier({ audience: 'hashbin.org', online: { apiKey: env.DBA_API_KEY } });

let result = await dba.verifyRequest(request, { action: 'hashbin:content:delete' });
if (!result.allow && result.online_required) result = await dba.verifyOnline(request, { action: 'hashbin:content:delete' });
if (!result.allow) return Response.json({ error: 'forbidden', code: result.code, reasons: result.reasons }, { status: result.status });

Other helpers: verify(credential) (signature, claims and revocation only), isRevoked(payload), decide(payload, check), and the lower-level verifyCredential, verifyProof, evaluateGrants, describeGrant and inspectCredential. Python and Go examples are in docs/samples.

Cloudflare Worker middleware

A complete Worker that guards routes by action and applies revocation webhooks. Requests from Cloudflare carry request.cf, so network-location constraints (countries, regions, areas) work without configuration.

import { createVerifier } from '@devicebasedauth/verify';

// Module scope: the verifier, its key and status-list caches, and its proof-replay cache live
// as long as the isolate, so most requests verify without any fetch.
let verifier;

const ROUTES = [
  { method: 'POST', pattern: /^\/api\/content$/, action: 'hashbin:content:write', handle: () => ({ published: true }) },
  { method: 'DELETE', pattern: /^\/api\/content\/([^/]+)$/, action: 'hashbin:content:delete', handle: ([, id]) => ({ deleted: id }) }
];

export default {
  async fetch(request, env = {}) {
    verifier ??= createVerifier({ issuer: env.DBA_ISSUER || 'https://devicebasedauth.org', audience: env.DBA_AUDIENCE || 'hashbin.org' });
    const { pathname } = new URL(request.url);
    // Revocation webhook (spec/events.md): register this URL on your audience. A signed
    // credentials.revoked event makes this verifier deny those credentials at once, before its
    // cached status list expires.
    if (request.method === 'POST' && pathname === '/webhooks/devicebasedauth') {
      const event = await verifier.handleEvent(await request.text());
      return Response.json(event.ok ? { received: event.type } : { error: event.message, code: event.code }, { status: event.ok ? 200 : event.status });
    }
    for (const route of ROUTES) {
      const match = request.method === route.method && pathname.match(route.pattern);
      if (!match) continue;
      // The resource lets grants limit a device to some paths ("resources": ["/api/content/abc*"]).
      const result = await verifier.verifyRequest(request, { action: route.action, resource: pathname });
      if (!result.allow) {
        const headers = result.status === 401 ? { 'WWW-Authenticate': 'DPoP algs="ES256"' } : {};
        return Response.json({ error: 'Not allowed', code: result.code, reasons: result.reasons }, { status: result.status, headers });
      }
      // result.account is the devicebasedauth.org account: map it to your own user.
      // result.caveats lists limits you enforce yourself, such as a monthly spending cap.
      return Response.json({ ...route.handle(match), account: result.account, device: result.device, caveats: result.caveats });
    }
    return Response.json({ error: 'Not found', code: 'not_found' }, { status: 404 });
  }
};

From docs/samples/worker-middleware.mjs, which runs in CI against a local server.

One replay cache for every isolate

The verifier remembers proof ids in memory, per isolate, so a captured proof could be replayed once against another isolate during its two-minute life. To close that, bind the ReplayCacheDO Durable Object in your own Worker and share it. It runs on your Cloudflare account; devicebasedauth.org is not involved and charges nothing. If the object cannot be reached the proof is refused (pass failOpen: true to accept instead).

// wrangler.toml
[[durable_objects.bindings]]
name = "DBA_REPLAY"
class_name = "ReplayCacheDO"
[[migrations]]
tag = "dba-replay-v1"
new_sqlite_classes = ["ReplayCacheDO"]

// worker.js
import { createVerifier, durableReplayCache } from '@devicebasedauth/verify';
export { ReplayCacheDO } from '@devicebasedauth/verify';
verifier ??= createVerifier({ audience: 'hashbin.org', replay: durableReplayCache(env.DBA_REPLAY) });

Online authorization API

POST /api/v1/authorize decides one request with everything offline verification cannot do: instant revocation, usage counters, step-up approval and a decision log the device owner can read. Every decision — allow or deny — costs the decision price and is billed to the audience's owner, so only the owner of an audience may ask about it. Authenticate with an account API key holding the authorize scope.

POST /api/v1/authorize
Authorization: ApiKey dbak_…
Content-Type: application/json

{
  "credential": "<the device credential>",
  "proof": "<the DPoP proof the device sent>",
  "request": { "method": "POST", "url": "https://hashbin.org/api/content" },
  "audience": "hashbin.org",
  "action": "hashbin:content:write",
  "resource": "optional",
  "context": { "network": { "country": "US", "region": "US-MO", "ip": "203.0.113.7" } }
}
{
  "allow": true, "code": "ok", "grant_index": 0, "reasons": [],
  "per_grant_reasons": [[]], "caveats": { "spend_usd_per_month": 5 },
  "device_id": "dev_…", "account": "user_…", "cid": "crd_…",
  "expires_in": 30, "cost_microdollars": 14
}

A positive answer may be cached for expires_in seconds (0 when counters or step-up were involved). A step-up grant answers {"allow": false, "code": "step_up_required", "step_up": {"id", "expires_in", "approve_url"}}; the owner approves it under Approvals (or GET /api/v1/step-ups and POST /api/v1/step-ups/{id}/approve or /deny, signed in; browsers with security notices on are told at once; a dashboard device cannot approve its own request, 403 self_approval) and the next request (within 5 minutes) is allowed once. Asking again while the request waits returns the same id; once the owner denies it, requests answer step_up_denied until it would have expired (10 minutes). Replayed proofs are refused with replayed_proof.

Gates: approvals and confirmation

A gate approves or refuses a use of a grant: the account owner (built in), one of the owner's devices, an authenticator app (TOTP), a security key or passkey, your own approval service (a webhook), Duo Push or Okta Verify. Add them on the dashboard's Gates page, or with POST /api/v1/gates (dba gates add; an API key holding gates:write, or a recent sign-in). An authenticator app or security key takes a second step: the answer's setup (a TOTP secret and otpauth_uri, or WebAuthn creation options) is finished within its expires_in by POST /api/v1/gates/{id}/activate with a first code or the registration. A grant names them in require.gates: a list of up to 3 entries that must all pass, each passed by any one of its gates.

{ "actions": ["hashbin:content:delete"],
  "require": { "gates": [{ "any": ["gate_…phone", "owner"], "timeout_s": 120, "on_timeout": "deny" }],
               "gates_reuse_s": 300 } }

Gated grants are checked online only (offline verifiers answer online_required). While the gates decide, POST /api/v1/authorize answers { "allow": false, "code": "gate_pending", "gate_request": { "id", "retry_after", "deadline" } }; pass that on as a 403 and the device asks again after retry_after seconds (the browser SDK's fetchWithGates() and the CLI's dba curl --dba-wait do this). A refusal is gate_denied. If nobody answers by the deadline the entry follows on_timeout (default deny; an allow by timeout is announced to the owner). An audience can require gates for an action, of certain kinds, and forbid allows by timeout, in its catalog (audience console, "Gate policies"). Each gate contacted is charged to the account that owns the gates (Pricing).

Gates answer in their own way: the owner in the dashboard's Approvals page; a device holding dba:approvals:answer with GET /api/v1/gate-requests and POST /api/v1/gate-requests/{id}/answer (each request lists the device's own gates in answer_as; dba approvals in the CLI); authenticator apps and security keys on the approval page linked from the owner's notice (/gate.html, over GET /api/v1/gate-links/{token} and POST …/answer); a webhook service by answering devicebasedauth.org's signed POST (spec/events.md §6); Duo and Okta in their apps.

Periodic confirmation. A credential issued with confirm: { gates, every_s } (chosen by the owner on the approval page, or sent to POST /api/v1/credentials) works only while its device holds a recent confirmation: the device calls POST /api/v1/credentials/{cid}/confirm, its gates approve, and it receives a dba-confirmation+jwt to send as the DBA-Confirmation header. Offline verifiers check it like the credential (signature, the same cid, sub and key); the dashboard's "Stop trusting now" ends it at once for online checks. The CLI (dba confirm, then automatically) and the browser SDK (confirm(), then automatically) keep one current.

Sign-in gates hold a Sign in with devicebasedauth.org (per site or by default), or the dashboard itself, until gates approve; see Sign in. They are read with GET /api/v1/settings/sign-in-gates ({ default, audiences, dashboard }) and set with PUT; until the dashboard's own gate approves, a dashboard sign-in can only confirm itself (POST /api/v1/session/confirm, or POST /api/v1/session/recover with a recovery code), and anything else answers 403 sign_in_gate_required. Changing them needs a dashboard session (a signed-in browser, or a device holding dba:session) and a recent sign-in; API keys and other devices get 403 session_required. A change that loosens them (removing gates, letting more gates or a timeout pass) waits until their current gates approve that exact change, so a stolen session cannot switch them off.

Samples run in CI: an approval service in Node and Python, and a CLI device that approves another's confirmation.

Sign in with devicebasedauth.org

devicebasedauth.org is an OpenID Connect provider (authorization code flow with PKCE S256; public clients, no client secret). Register your site as an audience with its redirect URIs; your client_id is the audience name. Discovery: /.well-known/openid-configuration.

// 1. Send the browser to the authorization endpoint.
const verifier = base64url(crypto.getRandomValues(new Uint8Array(32)));
const challenge = base64url(new Uint8Array(await crypto.subtle.digest('SHA-256', new TextEncoder().encode(verifier))));
const url = new URL('https://devicebasedauth.org/oauth/authorize');
url.search = new URLSearchParams({
  client_id: 'example.com', redirect_uri: 'https://example.com/auth/dba/callback', response_type: 'code',
  scope: 'openid profile device', state, nonce, code_challenge: challenge, code_challenge_method: 'S256'
});
location.assign(url);

// 2. On your callback, exchange the code (form-encoded or JSON).
const tokens = await fetch('https://devicebasedauth.org/oauth/token', {
  method: 'POST', headers: { 'Content-Type': 'application/x-www-form-urlencoded' },
  body: new URLSearchParams({ grant_type: 'authorization_code', code, redirect_uri, client_id: 'example.com', code_verifier: verifier })
}).then(r => r.json());
// tokens.id_token (ES256, verify with /.well-known/jwks.json), tokens.access_token, expires_in: 600

The ID token's sub and acct are the devicebasedauth.org account; when the user signed in with a device credential it also carries dev, cid and device_name, and amr is ["dba_device"] rather than ["session"]. GET /oauth/userinfo with the access token returns the same identity. Each sign-in costs the login price, billed to the audience's owner. For device-bound sessions on your own site (revoking the device ends access), accept DBA credentials on your API as in server verification.

MCP for agents

An agent can manage credentials through the Model Context Protocol endpoint POST /mcp (stateless Streamable HTTP, JSON-RPC 2.0). Authenticate with an account API key (Authorization: ApiKey dbak_…) whose scopes cover what the agent should do, or with a device credential. Each tool calls the ordinary API with the caller's own credential, at the ordinary prices.

MCP clients that support OAuth (the MCP authorization spec) need no key: add https://devicebasedauth.org/mcp as a remote server. The first call gets a 401 pointing at /.well-known/oauth-protected-resource/mcp (authorization server metadata: /.well-known/oauth-authorization-server); the client registers itself at /oauth/register (public client, PKCE), and you approve it on a consent page that lists the scopes it asked for (read-only account:read credentials:read transactions:read when it names none), after a recent sign-in. The connection then appears under API keys in the dashboard, with the same metered reads as a key, and revoking it there stops it at once. Access tokens last an hour; each refresh costs the token price from your balance, refresh tokens rotate on every use, and replaying an old one revokes the connection. With an empty balance a refresh answers 503 temporarily_unavailable and the refresh token keeps working after a deposit.

Agent-friendly defaults: short lifetimes, a spend cap (limits.spend_usd_per_month), and require.online so the owner sees every decision. A summary for language models is at /llms.txt.

Revocation and status lists

  • Revoke one credential (DELETE /api/v1/credentials/{cid}), every credential of a device (POST /api/v1/devices/{id}/revoke), everything — optionally for one audience — (POST /api/v1/revoke-all with {"confirm": "revoke-all"}), or let a device revoke itself (POST /api/v1/self/revoke). Credentials a device delegated are revoked with it. A revoked device stays revoked: an enrollment token or a delegating device cannot issue to its key again (403 device_revoked); only the account owner, signed in within the last 10 minutes (or with an API key), can, which reinstates it.
  • Revocation is free: its cost is prepaid in the issue price, so it works at a zero balance.
  • Online checks (/api/v1/authorize, and this service's own API) see a revocation immediately.
  • Offline verifiers see it through the credential's status list, republished within about a minute and cached by verifiers for at most their TTL (we publish 60 s; verifiers should cache ≤ 5 minutes). Short credential lifetimes with automatic renewal bound the window further.
  • Audiences can also be told at once: set revocation_webhook on your audience (PATCH /api/v1/audiences/{name}, an https URL on your own domain, or in the dashboard). Each revocation of a credential naming your audience is POSTed as a dba-event+jwt signed with the issuer key; verifier.handleEvent(body) checks it and denies those credentials immediately (see the Worker sample). Delivery is retried after 1 minute, 10 minutes and 1 hour, costs audiences nothing, and never replaces the status list. Format: spec/events.md.

Status lists follow the IETF OAuth Token Status List draft: a JWT (typ: statuslist+jwt) signed by the issuer whose sub is the list URL and whose status_list.lst is a zlib-compressed, base64url bitstring, 1 bit per credential, least significant bit first. Fetch them from the uri in the credential (e.g. /status/v1/lists/0); verifiers must fail closed when a list cannot be fetched.

Renewal, rotation and access tokens

POST /api/v1/credentials/{cid}/renew, authenticated by the credential and a proof, issues the next version with a fresh expiry (the renew price); grants never widen. Add new_key_proof (a dba-rotate+jwt signed by the new key) to move to a new key, which revokes the old one. POST /api/v1/token with {"audience"} trades a credential for a ≤ 10-minute bearer token carrying only that audience's grants, for scripts that can only set one header; audiences may refuse them.

If an issuer key is ever withdrawn (after a compromise; see the runbook), it leaves the JWKS and relying parties refuse what it signed. Devices do not re-enroll: the same renew call accepts a credential signed by a withdrawn key when it is exactly the one devicebasedauth.org issued and stored, and returns one signed by the current key, with "recovered": true and no charge. The browser SDK's autoRenew() and the CLI notice the missing key in the JWKS (the CLI checks at most hourly) and do this by themselves; dba.keyWithdrawn() asks directly.

X.509 client certificates (mTLS)

Sites that authenticate with mutual TLS, such as Cloudflare API Shield, can trust devicebasedauth.org's device CA: add /.well-known/dba-ca.pem to the trust store. A device then trades its credential for a certificate over its own key with POST /api/v1/certificate ({"lifetime_seconds"}, 5 minutes to 24 hours, default 1 hour; the token price), or from the CLI:

dba certificate                  # writes client.crt, client.key and ca.crt in the profile directory
curl --cert ~/.config/dba/default/client.crt --key ~/.config/dba/default/client.key https://api.example.com/

The certificate's CN is the device id and its subjectAltName holds urn:devicebasedauth:device:…, …:credential:… and …:account:… URIs. It carries no grants and mTLS cannot see revocation, so it only proves the client holds a device key vouched for in the last day; decide actions from the credential (spec §6a).

API conventions and errors

  • REST and JSON under /api/v1/. The full list is /openapi.json, generated from the route table.
  • Authentication: a dashboard session, an account API key (Authorization: ApiKey dbak_…, scoped: account:read, transactions:read, credentials:read, credentials:issue, credentials:revoke, audiences:read, audiences:write, authorize, gates:read, gates:write, networks:read, networks:write; approvals:answer is for devices only), or a devicebasedauth.org device credential with a proof whose grants hold dba:<scope> or dba:session — this site is its own first audience. Grants with dba: actions may use time, place and attestation constraints but not limits.uses or require.step_up (refused at issuance; this site keeps no counters or approvals for itself). An API key (or an app connected over OAuth) can put dba: actions in a credential or an enrollment token only within its own scopes, each named exactly: a key with credentials:issue and credentials:read may grant dba:credentials:issue and dba:credentials:read, never dba:session or a wildcard such as dba:* (403 insufficient_scope).
  • API keys are made by the signed-in owner, after a recent sign-in: POST /api/v1/keys with { "name", "scopes": [...] } answers the dbak_… secret once; GET /api/v1/keys lists keys and connected apps, DELETE /api/v1/keys/{id} revokes one. A signed-in owner deposits with POST /api/v1/payments/checkout ({ "credit_cents" }, an Idempotency-Key recommended), which answers a Stripe Checkout url.
  • Money is integer micro-dollars. Every response includes cost_microdollars and the header X-DBA-Cost-Microdollars; a billable response also includes balance_microdollars and X-DBA-Balance-Microdollars (what is left) when the caller may read the account (account:read, or the dashboard). GET /api/v1/quote?op=issue prices an operation. ?dry_run=1 on any billable call (issue, approve, redeem, sign-up completion, renew, confirm, token, certificate, authorize, audience changes; not address-list changes) does nothing but answer { "dry_run": true, "op", "price_microdollars" }, plus balance_microdollars and sufficient for callers who may read the account (charged as a read to API keys); on a checkout it previews the card fee.
  • Send an Idempotency-Key (1–128 printable ASCII characters) when issuing credentials with POST /api/v1/credentials: a retry with the same key returns the credential the first request issued, charged once ("idempotent_replay": true); the same key with a different request is refused with 422 idempotency_key_reused. Approving an enrollment is idempotent by itself. Renewal is too: a second renewal of the same version answers 409 superseded.

Pricing

Prepaid micro-dollars, no subscription, $5 minimum deposit with the card fee itemized, offline verification free. The issuing account pays to issue and renew, and for its gates, confirmations and security emails; the audience pays for online decisions and sign-ins, and its owner to register or change it; the owner of a named address list pays to create or change it; API-key reads are paid by the caller. See Pricing for live prices and a calculator.
