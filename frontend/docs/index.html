Concepts

devicebasedauth.org issues device credentials: signed, readable statements of what one device may do, for which sites, when and where. The device holds the private key; we only ever see the public key.

TermMeaning
AccountA devicebasedauth.org customer with a prepaid balance in micro-dollars. Its id appears in credentials as acct.
DeviceAnything that can hold a private key: a browser profile, phone, laptop, server, CLI, CI job or AI agent. Identified by dev_… and its key thumbprint.
AudienceA site or API that accepts credentials (a domain such as hashbin.org). It owns an action namespace and publishes an action catalog.
ActionA namespaced verb from a catalog: hashbin:content:write, cronly:run, dba:session. ns:* matches every action in a namespace.
Grant{ actions, resources, when, where, limits, require }. A credential holds 1–32 grants; a request is allowed when at least one grant passes. Nothing is allowed by default.
CredentialA compact JWS (ES256) signed by devicebasedauth.org binding a device public key to grants for one or more audiences.
ProofA DPoP proof (RFC 9449): a tiny JWS signed by the device key for one request (method, URL, time, credential hash).
Status listA signed, compressed bitstring; bit n set means the credential at index n is revoked.
EnrollmentThe device sends its public key and the grants it wants; the account owner approves (or narrows) them on an approval page; the credential is issued.

How it fits together

  1. The device makes a key pair (non-extractable where the platform allows) and asks to enroll.
  2. The account owner opens the approval link, reads the request in plain English, and approves it. The account pays the issue price.
  3. The device sends Authorization: DBA <credential> and a fresh DPoP proof with each request.
  4. The site verifies offline with @devicebasedauth/verify (free), or asks POST /api/v1/authorize for usage limits, step-up approval and instant revocation (metered, paid by the site).
  5. The owner can revoke the credential, the device, or everything, at any time.

The credential format

A credential is header.payload.signature, each base64url. The payload is plain JSON; decode it with one base64url decode, or paste it into the inspector. The normative description is spec/credential.md; grant evaluation is spec/evaluation.md, with conformance vectors in spec/vectors.

{ "typ": "dba-device+jwt", "alg": "ES256", "kid": "dba-2026-11" }
.
{
  "iss": "https://devicebasedauth.org",
  "sub": "dev_7Q2M9X4K1B",
  "acct": "user_2abc",
  "aud": ["hashbin.org"],
  "cid": "crd_K3J8P1W6ZQ",
  "jti": "crd_K3J8P1W6ZQ.1",
  "iat": 1795017600, "nbf": 1795017600, "exp": 1797609600,
  "cnf": { "jkt": "0ZcOCORZNYy-DWpqq30jZyJGHTN0d2HglBV3uiguA4I" },
  "device": { "name": "Laptop — Firefox", "kind": "browser", "key_protection": "webcrypto-nonextractable" },
  "grants": [{
    "actions": ["hashbin:content:write"],
    "when": { "tz": "America/Chicago", "windows": [{ "days": ["mon","tue","wed","thu","fri"], "from": "08:00", "to": "18:00" }] },
    "where": { "source": "network", "countries": ["US"] },
    "limits": { "spend_usd_per_month": 5 }
  }],
  "status": { "status_list": { "idx": 48213, "uri": "https://status.devicebasedauth.org/v1/lists/7" } },
  "ver": 1
}

Present it with a proof made by the device key:

Authorization: DBA <credential>
DPoP: <proof: {"typ":"dpop+jwt","alg":"ES256","jwk":{…}} . {"jti","htm","htu","iat","ath"[,"nonce"][,"loc"]}>

Credentials are not secret — they are useless without the private key — but every site you show one to can read its device name and places. Keep geofences coarse and device names generic where that matters. Unknown grant members make that grant deny, so new constraint types can never silently over-grant on old verifiers.

Quick start: browser SDK

The SDK makes a non-extractable P-256 key with WebCrypto and keeps it in IndexedDB: scripts on your origin can sign with it, but nothing can read it out. Enrollment opens the approval page in a popup, so call it from a click handler. Pin a versioned copy with Subresource Integrity in production (/sdk/v1.0.0/dba.js).

<script type="module">
  import { DBA } from 'https://devicebasedauth.org/sdk/dba.js';

  const dba = new DBA();            // new DBA({ origin, name }) for another server or a second identity
  document.querySelector('#connect').addEventListener('click', async () => {
    if (!await dba.ready()) {
      await dba.enroll({
        aud: ['hashbin.org'],
        grants: [{ actions: ['hashbin:content:write'], limits: { spend_usd_per_month: 5 } }],
        device: { name: 'Notes app on my laptop' },
        lifetime_seconds: 30 * 86400
      });
    }
    dba.autoRenew();                 // renews at 2/3 of the lifetime while the page is open
    const response = await dba.fetch('https://hashbin.org/api/content', { method: 'POST', body: 'hello' });
    console.log(response.status, dba.describe());
  });
</script>
MethodWhat it does
ready()Loads the stored key and credential; true when an unexpired credential exists.
enroll(request, { popup, onApprovalUrl, timeoutMs })Signs an enrollment request with a new key, opens the approval page and resolves with the credential (by postMessage, or by polling when approved elsewhere).
fetch(input, init)fetch() with the credential and a fresh proof attached.
headers(method, url)Just the Authorization and DPoP headers for one request.
allows(action, { resource, location })A local hint for UI (time, place and action checks only); servers still decide.
payload, describe(), expiresIn()The decoded credential, its grants in plain English, seconds left.
renew({ rotate }), autoRenew()Renew (or move to a new key) before expiry.
token(audience)A 10-minute bearer access token for code that cannot sign each request.
revoke(), forget()Revoke this credential everywhere and delete the key; or only delete it locally.

Quick start: CLI

The dba CLI keeps the key in a 0600 file under ~/.config/dba/<profile>/ and never sends it anywhere. dba help lists every command.

# 1. Make a key and ask for permission to publish on hashbin.org. This prints a link; the
#    account owner opens it, checks the grants and approves. The command waits for that.
dba enroll --aud hashbin.org --action hashbin:content:write --name "Sample laptop" --wait 300

# 2. What may this device do?
dba status

# 3. Headers for one request (the DPoP proof is single-use and names this method and URL).
dba headers POST https://hashbin.org/api/content

From docs/samples/enroll-and-call.sh, which runs in CI against a local server.

dba curl -sS https://hashbin.org/api/content -d 'hello'          # curl with the headers added
curl -H "Authorization: Bearer $(dba token --aud hashbin.org)" https://hashbin.org/api/content
dba enroll --aud hashbin.org --grant '{"actions":["hashbin:content:*"],"where":{"source":"network","countries":["US"]}}'
dba renew --rotate                                                 # renew onto a fresh key
dba revoke                                                         # revoke and delete the key

Like the browser SDK, the CLI renews for you: dba headers, sign, curl, token and status --online renew the credential first once two thirds of its lifetime has passed. If that fails (say the balance is too low) they warn and use the current credential, which is still valid. A device that runs rarely can renew from cron with dba renew --if-due; turn automatic renewal off with --no-renew or DBA_AUTO_RENEW=0.

Agents and other programs that cannot wait can use dba enroll --print-request to get a signed request, submit it (for example through the MCP request_enrollment tool), and finish with dba import.

Fleets: enrollment tokens

To enroll many machines without approving each one, create an enrollment token in the dashboard (Enrollment tokens) or with POST /api/v1/enrollment-tokens ({name, aud, grants, lifetime_seconds, max_uses, expires_in_days}; a session or an API key with credentials:issue). The dbae_… secret is shown once. Each machine still makes its own key, then:

DBA_ENROLLMENT_TOKEN=dbae_… dba enroll --name build-runner-7        # the token's aud and grants apply
await dba.enroll({ device: { name: 'Kiosk 1' } }, { enrollmentToken }) // browser SDK, no popup

Under the hood that is POST /api/v1/enrollments/redeem with {request, enrollment_token}, where request is the usual dba-enroll+jwt; it may narrow the token's audiences, grants and lifetime but never widen them. Each device costs the issue price, paid by the token's account; the token stops after max_uses devices (at most 10,000), on its expiry (at most 90 days), or when revoked. Credentials record which token issued them. A device signed in with a delegated credential cannot create tokens.

Verify requests on your server

@devicebasedauth/verify is a zero-dependency ES module for Workers, Node 22+, Deno, Bun and browsers. It fetches and caches the issuer's JWKS (1 hour) and status lists (at most 5 minutes) and keeps a proof-replay cache, so most requests verify without any network call. Create one verifier per process and reuse it.

const dba = createVerifier({ issuer, audience: 'hashbin.org' });

/** What a route handler does: verify, then allow or refuse with the reasons. */
async function check(label, request, action) {
  const result = await dba.verifyRequest(request, { action });

From docs/samples/verify-request.mjs, which runs in CI against a local server.

verifyRequest(request, { action, resource, location }) returns { allow, status, code, reasons, grant_index, caveats, online_required, account, device, credential_id, credential }. status is the HTTP status to answer with: 401 for a missing, invalid, replayed or revoked credential, 403 when no grant allows the action, 503 when keys or status lists cannot be fetched (it fails closed). Map account to your own user once (for example with Sign in with devicebasedauth.org) and refuse unlinked accounts.

When to go online

Grants with limits.uses, require.online or require.step_up deny offline with code: "online_required". Ask devicebasedauth.org instead — metered at the decision price and paid by your audience account — with an API key that has the authorize scope:

import { createVerifier } from '@devicebasedauth/verify';

const dba = createVerifier({ audience: 'hashbin.org', online: { apiKey: env.DBA_API_KEY } });

let result = await dba.verifyRequest(request, { action: 'hashbin:content:delete' });
if (!result.allow && result.online_required) result = await dba.verifyOnline(request, { action: 'hashbin:content:delete' });
if (!result.allow) return Response.json({ error: 'forbidden', code: result.code, reasons: result.reasons }, { status: result.status });

Other helpers: verify(credential) (signature, claims and revocation only), isRevoked(payload), decide(payload, check), and the lower-level verifyCredential, verifyProof, evaluateGrants, describeGrant and inspectCredential. Python and Go examples are in docs/samples.

Cloudflare Worker middleware

A complete Worker that guards routes by action and applies revocation webhooks. Requests from Cloudflare carry request.cf, so network-location constraints (countries, regions, areas) work without configuration.

import { createVerifier } from '@devicebasedauth/verify';

// Module scope: the verifier, its key and status-list caches, and its proof-replay cache live
// as long as the isolate, so most requests verify without any fetch.
let verifier;

const ROUTES = [
  { method: 'POST', pattern: /^\/api\/content$/, action: 'hashbin:content:write', handle: () => ({ published: true }) },
  { method: 'DELETE', pattern: /^\/api\/content\/([^/]+)$/, action: 'hashbin:content:delete', handle: ([, id]) => ({ deleted: id }) }
];

export default {
  async fetch(request, env = {}) {
    verifier ??= createVerifier({ issuer: env.DBA_ISSUER || 'https://devicebasedauth.org', audience: env.DBA_AUDIENCE || 'hashbin.org' });
    const { pathname } = new URL(request.url);
    // Revocation webhook (spec/events.md): register this URL on your audience. A signed
    // credentials.revoked event makes this verifier deny those credentials at once, before its
    // cached status list expires.
    if (request.method === 'POST' && pathname === '/webhooks/devicebasedauth') {
      const event = await verifier.handleEvent(await request.text());
      return Response.json(event.ok ? { received: event.type } : { error: event.message, code: event.code }, { status: event.ok ? 200 : event.status });
    }
    for (const route of ROUTES) {
      const match = request.method === route.method && pathname.match(route.pattern);
      if (!match) continue;
      // The resource lets grants limit a device to some paths ("resources": ["/api/content/abc*"]).
      const result = await verifier.verifyRequest(request, { action: route.action, resource: pathname });
      if (!result.allow) {
        const headers = result.status === 401 ? { 'WWW-Authenticate': 'DPoP algs="ES256"' } : {};
        return Response.json({ error: 'Not allowed', code: result.code, reasons: result.reasons }, { status: result.status, headers });
      }
      // result.account is the devicebasedauth.org account: map it to your own user.
      // result.caveats lists limits you enforce yourself, such as a monthly spending cap.
      return Response.json({ ...route.handle(match), account: result.account, device: result.device, caveats: result.caveats });
    }
    return Response.json({ error: 'Not found', code: 'not_found' }, { status: 404 });
  }
};

From docs/samples/worker-middleware.mjs, which runs in CI against a local server.

Online authorization API

POST /api/v1/authorize decides one request with everything offline verification cannot do: instant revocation, usage counters, step-up approval and a decision log the device owner can read. Every decision — allow or deny — costs the decision price and is billed to the audience's owner, so only the owner of an audience may ask about it. Authenticate with an account API key holding the authorize scope.

POST /api/v1/authorize
Authorization: ApiKey dbak_…
Content-Type: application/json

{
  "credential": "<the device credential>",
  "proof": "<the DPoP proof the device sent>",
  "request": { "method": "POST", "url": "https://hashbin.org/api/content" },
  "audience": "hashbin.org",
  "action": "hashbin:content:write",
  "resource": "optional",
  "context": { "network": { "country": "US", "region": "US-MO", "ip": "203.0.113.7" } }
}
{
  "allow": true, "code": "ok", "grant_index": 0, "reasons": [],
  "per_grant_reasons": [[]], "caveats": { "spend_usd_per_month": 5 },
  "device_id": "dev_…", "account": "user_…", "cid": "crd_…",
  "expires_in": 30, "cost_microdollars": 10
}

A positive answer may be cached for expires_in seconds (0 when counters or step-up were involved). A step-up grant answers {"allow": false, "code": "step_up_required", "step_up": {"id", "expires_in", "approve_url"}}; the owner approves it under Approvals and the next request (within 5 minutes) is allowed once. Replayed proofs are refused with replayed_proof.

Sign in with devicebasedauth.org

devicebasedauth.org is an OpenID Connect provider (authorization code flow with PKCE S256; public clients, no client secret). Register your site as an audience with its redirect URIs; your client_id is the audience name. Discovery: /.well-known/openid-configuration.

// 1. Send the browser to the authorization endpoint.
const verifier = base64url(crypto.getRandomValues(new Uint8Array(32)));
const challenge = base64url(new Uint8Array(await crypto.subtle.digest('SHA-256', new TextEncoder().encode(verifier))));
const url = new URL('https://devicebasedauth.org/oauth/authorize');
url.search = new URLSearchParams({
  client_id: 'example.com', redirect_uri: 'https://example.com/auth/dba/callback', response_type: 'code',
  scope: 'openid profile device', state, nonce, code_challenge: challenge, code_challenge_method: 'S256'
});
location.assign(url);

// 2. On your callback, exchange the code (form-encoded or JSON).
const tokens = await fetch('https://devicebasedauth.org/oauth/token', {
  method: 'POST', headers: { 'Content-Type': 'application/x-www-form-urlencoded' },
  body: new URLSearchParams({ grant_type: 'authorization_code', code, redirect_uri, client_id: 'example.com', code_verifier: verifier })
}).then(r => r.json());
// tokens.id_token (ES256, verify with /.well-known/jwks.json), tokens.access_token, expires_in: 600

The ID token's sub and acct are the devicebasedauth.org account; when the user signed in with a device credential it also carries dev, cid and device_name, and amr is ["dba_device"] rather than ["session"]. GET /oauth/userinfo with the access token returns the same identity. Each sign-in costs the login price, billed to the audience's owner. For device-bound sessions on your own site (revoking the device ends access), accept DBA credentials on your API as in server verification.

MCP for agents

An agent can manage credentials through the Model Context Protocol endpoint POST /mcp (stateless Streamable HTTP, JSON-RPC 2.0). Authenticate with an account API key (Authorization: ApiKey dbak_…) whose scopes cover what the agent should do, or with a device credential. Each tool calls the ordinary API with the caller's own credential, at the ordinary prices.

ToolDoes
whoamiDescribe the credential the agent is using.
balancePrepaid balance and this month's spend.
list_credentialsIssued credentials (filters: status, audience, device).
get_credentialOne credential with its grants in plain English and its history.
request_enrollmentSubmit a signed enrollment request (dba enroll --print-request makes one); returns an approval_url for a human. Nothing is charged until a human approves.
revoke_credentialRevoke a credential immediately (free).
quotePrice of an operation in micro-dollars.
inspect_credentialDecode and verify a credential; optionally check an action.
evaluate_grantsEvaluate grants for an action at a time and place, offline and free.
curl -sS https://devicebasedauth.org/mcp \
  -H "Authorization: ApiKey $DBA_API_KEY" -H 'Content-Type: application/json' \
  -d '{"jsonrpc":"2.0","id":1,"method":"tools/call","params":{"name":"evaluate_grants","arguments":{"grants":"[{\"actions\":[\"hashbin:content:write\"]}]","action":"hashbin:content:write"}}}'

Agent-friendly defaults: short lifetimes, a spend cap (limits.spend_usd_per_month), and require.online so the owner sees every decision. A summary for language models is at /llms.txt.

Revocation and status lists

  • Revoke one credential (DELETE /api/v1/credentials/{cid}), every credential of a device (POST /api/v1/devices/{id}/revoke), everything — optionally for one audience — (POST /api/v1/revoke-all with {"confirm": "revoke-all"}), or let a device revoke itself (POST /api/v1/self/revoke). Credentials a device delegated are revoked with it.
  • Revocation is free: its cost is prepaid in the issue price, so it works at a zero balance.
  • Online checks (/api/v1/authorize, and this service's own API) see a revocation immediately.
  • Offline verifiers see it through the credential's status list, republished within about a minute and cached by verifiers for at most their TTL (we publish 60 s; verifiers should cache ≤ 5 minutes). Short credential lifetimes with automatic renewal bound the window further.
  • Audiences can also be told at once: set revocation_webhook on your audience (PATCH /api/v1/audiences/{name}, an https URL on your own domain, or in the dashboard). Each revocation of a credential naming your audience is POSTed as a dba-event+jwt signed with the issuer key; verifier.handleEvent(body) checks it and denies those credentials immediately (see the Worker sample). Delivery is retried after 1 minute, 10 minutes and 1 hour, costs audiences nothing, and never replaces the status list. Format: spec/events.md.

Status lists follow the IETF OAuth Token Status List draft: a JWT (typ: statuslist+jwt) signed by the issuer whose sub is the list URL and whose status_list.lst is a zlib-compressed, base64url bitstring, 1 bit per credential, least significant bit first. Fetch them from the uri in the credential (e.g. /status/v1/lists/0); verifiers must fail closed when a list cannot be fetched.

Renewal, rotation and access tokens

POST /api/v1/credentials/{cid}/renew, authenticated by the credential and a proof, issues the next version with a fresh expiry (the renew price); grants never widen. Add new_key_proof (a dba-rotate+jwt signed by the new key) to move to a new key, which revokes the old one. POST /api/v1/token with {"audience"} trades a credential for a ≤ 10-minute bearer token carrying only that audience's grants, for scripts that can only set one header; audiences may refuse them.

API conventions and errors

  • REST and JSON under /api/v1/. The full list is /openapi.json, generated from the route table.
  • Authentication: a dashboard session, an account API key (Authorization: ApiKey dbak_…, scoped: account:read, transactions:read, credentials:read, credentials:issue, credentials:revoke, audiences:read, audiences:write, authorize), or a devicebasedauth.org device credential with a proof whose grants hold dba:<scope> or dba:session — this site is its own first audience.
  • Money is integer micro-dollars. Every response includes cost_microdollars and the header X-DBA-Cost-Microdollars. GET /api/v1/quote?op=issue prices an operation; ?dry_run=1 previews a checkout.
  • Send an Idempotency-Key (≤ 128 characters) on POSTs that cost money; retries with the same key are charged once.

Errors are JSON { "error": "message", "code": "machine_code", … }:

Verifiers report decision reasons per grant, such as action_not_granted, outside_time_window, outside_location:network, network_not_allowed, location_stale:device and online_required; see spec/evaluation.md.

Pricing

Prepaid micro-dollars, no subscription, $5 minimum deposit with the card fee itemized, offline verification free. The issuing account pays to issue and renew; the audience pays for online decisions and sign-ins; API-key reads are paid by the caller. See Pricing for live prices and a calculator.
