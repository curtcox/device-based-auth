Network rules and address lists

A grant's net member limits the connection a request arrives on: from which addresses, and how far away in round-trip time. It is evidence about the connection, not proof of identity; the device key still proves who is talking. The rest of the API is the same as for every grant: see the docs.

The net member

A credential with any grant that has net carries "ver": 2; verifiers that only know vocabulary 1 deny such grants (unknown_constraint:net), so the rule fails closed everywhere. The normative rules are spec/evaluation.md §3.10, with conformance vectors.

{ "actions": ["hashbin:content:write"],
  "net": {
    "client": {
      "addresses": { "cidrs": ["203.0.113.0/24"],
                     "lists": [{ "id": "adl_OFFICE0001", "uri": "https://status.devicebasedauth.org/v1/addresses/adl_OFFICE0001" }],
                     "dns": { "names": ["vpn-egress.example.com"], "dnssec": true } },
      "latency": { "max_rtt_ms": 40, "samples": 1, "reuse_s": 60 }
    }
  } }

net needs client or server; each needs at least one of addresses, route or latency, and every one present must pass. Verifiers evaluate only client: the request's source as the relying party sees it. server is a rule for the device's own SDK or CLI about which servers it sends to; it is validated at issuance and ignored by verifiers, and no released client enforces it yet. route (signed relay hops) and addresses.webhook (an approval service asked about an address) are accepted at issuance, but neither the verify library nor POST /api/v1/authorize supplies the context they need yet: until they are built, a client rule with route denies everywhere, and an addresses.webhook source matches nothing (a grant relying on it alone denies).

where.networks (vocabulary 1) still works and is checked with where; use net when you need lists, DNS or round-trip time.

Addresses

net.client.addresses checks the peer address the verifier sees. By default the JavaScript verifier reads it from CF-Connecting-IP, which Cloudflare sets and clients cannot forge on Cloudflare. Anywhere else a client can send that header itself: outside Cloudflare, strip it at your edge or pass the socket address as check.location.network.ip. Its sources form a union: the address passes when any one of them allows it.

SourceAllows the address when
cidrsIt is inside one of 1–64 IPv4 or IPv6 ranges written into the grant.
listsIt is inside a range of one of 1–8 named address lists the verifier holds a current copy of. Change the list and every grant naming it changes, without reissuing.
dnsIt equals one of the A or AAAA addresses of 1–16 host names, resolved by the verifier. With "dnssec": true, only DNSSEC-validated answers count.

A source the verifier could not consult (a list it cannot fetch, a name that does not resolve) matches nothing: network rules never allow by failing.

Named address lists

A named address list is a set of up to 10,000 IPv4 and IPv6 ranges that your account owns (at most 50 lists). devicebasedauth.org publishes each one as a signed dba-addresses+jwt at https://status.devicebasedauth.org/v1/addresses/{id} (spec §7a), so any verifier can enforce it offline. Changes are published within about a minute, and verifiers cache a copy for 60 seconds.

RouteAccessWhat it does
GET /api/v1/address-lists, GET /api/v1/address-lists/{id}networks:readList your lists, or read one with its ranges. Each has id, name, uri, count, ver and published_until.
POST /api/v1/address-listsnetworks:writeCreate one: { "name": "Office", "cidrs": ["192.0.2.0/24", "2001:db8:42::/48"] }. Ranges are de-duplicated and sorted; a range with host bits set (192.0.2.7/24) is refused, and a single address needs /32 or /128.
PUT /api/v1/address-lists/{id}networks:write, recent sign-inReplace its ranges (and optionally its name). The list may be empty.
DELETE /api/v1/address-lists/{id}networks:write, recent sign-inDelete it (free). It is published as a tombstone that matches nothing, so every grant naming it denies.

Replacing and deleting need a recent sign-in, like changing gates (confirming it is you), or an API key: widening a list widens every grant that names it. A grant names a list by its id and exactly the uri the API returns, and devicebasedauth.org issues grants only for live lists of the issuing account (400 unknown_address_list otherwise).

Price. A create or replace costs the address_list price per started 1,000 ranges, plus the address_list_day price for each day it extends the list's published life to 13 months from now: a new list of up to 1,000 ranges prepays 395 days, about 6,200 µ$ ($0.006), and changing it a day later pays for one more day. A list not changed for 13 months stops being re-signed and expires, which denies every grant naming it. Live prices: Pricing.

Lists are readable by anyone who has the URI, which every site shown the credential has, so do not put anything private in a list's ranges. Grants with dba: actions (this site's own API) cannot use lists yet; they deny there.

Round-trip time

net.client.latency bounds how far away (in network time) the device may be: max_rtt_ms (1–5,000, required), samples (1–5, the verifier keeps the best of that many measurements) and reuse_s (0–300, how long a passing measurement counts for the same key and address). The verifier answers the first request with 401 use_dpop_nonce and a timed nonce; the device's retry, signed with that nonce, is timed. A device can answer later but never sooner, so the measurement is only ever an upper bound: it stops a credential being used from far away, not a stolen key used nearby.

The browser SDK's fetch(), api() and fetchWithGates() answer up to three timed challenges in the current /sdk/dba.js; the pinned releases up to v1.4.0 answer only the plain nonce challenge, once, so they cannot pass a grant with samples above 1. dba headers, dba sign and dba curl hand the proof to another program that cannot answer the challenge, so they refuse a credential whose every grant has latency (and warn when some do).

Verifier setup

createVerifier from @devicebasedauth/verify resolves what net needs before it evaluates:

const dba = createVerifier({
  audience: 'example.com',
  rtt: { secret: env.DBA_RTT_SECRET },   // 32+ bytes, the same on every instance; enables latency
  dns: true                              // resolve net.client.addresses.dns over DNS-over-HTTPS (1.1.1.1)
  // addressLists: on by default (60 s fresh, 10 minutes stale while fetches fail, never an older ver)
});

const result = await dba.verifyRequest(request, { action: 'example:write' });
if (!result.allow) {
  // A latency grant first answers 401 use_dpop_nonce: send result.headers (DPoP-Nonce) and
  // result.rtt so the device retries with the timed nonce.
  return Response.json({ error: 'Not allowed', code: result.code, reasons: result.reasons, rtt: result.rtt, dpop_nonce: result.dpop_nonce },
    { status: result.status, headers: result.headers });
}

Without rtt, pass location.network.rtt_ms yourself or latency grants deny with rtt_required. Without dns, names are unresolved and match nothing. addressLists: false stops fetching lists (they then match nothing); you can also pass your own resolvers (createDohResolver, createAddressListResolver, createRttChallenger are exported). Online, POST /api/v1/authorize reads named address lists itself and takes the peer address (and a measured rtt_ms, if you have one) from context.network; it does not resolve DNS names.

Reasons

ReasonMeaning
address_unavailableThe verifier did not know the peer address.
address_not_allowedNo source allows the address. It is followed by one informational reason per source that could not be consulted: address_list_unavailable:<id>, dns_unresolved:<name> or dns_unvalidated:<name>.
route_required, route_invalid:<why>, route_relay_not_allowedThe grant has a route rule and no accepted relay hops.
rtt_requiredNo round trip was measured: the verifier must challenge the device and try again.
rtt_exceededThe measured round trip was longer than max_rtt_ms.

The policy playground evaluates net grants against an IP address you enter; named lists, DNS names and round trips count as unavailable there.
